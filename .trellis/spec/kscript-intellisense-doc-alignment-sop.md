# KScript 智能提示与文档对齐 SOP

> 适用范围：核对 Kooboo 编辑器中实际提供智能提示的 KScript API，与 `docs/api/**`、`docs/en/api/**` 的覆盖和推荐状态。
> 核心原则：文档描述的是当前推荐使用的智能提示面，不是所有仍可运行的兼容 API。

## 1. 目标

每次对齐都要同时回答两个方向的问题：

1. **智能提示 → 文档**：当前推荐 API 中，哪些缺少文档、示例、导航或完整子模块？
2. **文档 → 智能提示**：当前文档中，哪些 API 已无智能提示、命名已漂移、仅为兼容入口或已被产品暂停推荐？

最终产物不是“把所有 `k.*` 都写进文档”，而是一份经过产品决策、运行验证和双语校验的推荐 API 集合。

## 2. 可文档化判定

一个 API 进入公开文档前，必须同时满足：

- 出现在当前最终智能提示定义中；
- 不属于 `[Obsolete]`、兼容保留或已有替代入口；
- 不在产品明确暂停的范围内；
- 签名、行为和适用条件能够由当前源码与真实运行证据确认；
- 至少有一个可公开、可复现且已执行通过的示例。

“运行时还能调用”不能单独作为文档化理由。反过来，智能提示是必要条件，但不是充分条件；例如动态生成的 Integration、Market 定义仍可因产品决策暂停公开。

## 3. 真相源与契约层

### 3.1 最终智能提示面

静态 `k` 定义的生成链为：

```text
Kooboo.Sites/Scripting/k.cs
  → TypeDefineConverter(typeof(k))
  → DefineStringify
  → KScriptService.GetDefine(WebSite)
  → KScript/GetDefine
  → Monaco 编辑器
```

`KScriptService.GetDefine(WebSite)` 还会按站点追加动态定义，包括 OpenAPI、Content、UserOptions、Commerce Custom Data，以及 Integration、Market 等定义。因此核对必须包含真实站点返回的 `KScript/GetDefine`，不能只看 `k.cs` 或静态 `kooboo.d.ts`。

### 3.2 各层职责

| 层 | 用途 | 不能替代什么 |
|----|------|--------------|
| `k.cs` 与公开类型源码 | 核对成员、属性、重载、`KIgnore`、`KeepCase`、`Obsolete` 和行为实现 | 不能完整代表站点动态提示 |
| `TypeDefineConverter` / `KScriptService.GetDefine` | 判断智能提示如何生成、哪些成员最终可见 | 不能证明方法运行结果 |
| 真实站点 `KScript/GetDefine` | 取得用户实际看到的最终提示面 | 不能证明示例可执行 |
| `old-source/kooboo.d.ts` | 发现历史类型和漂移 | 不是当前真相源 |
| 旧文档与 skill reference | 复用表述、场景和历史线索 | 不能作为签名或行为的唯一证据 |
| ai-check + live HTTP/站点执行 | 证明示例、返回值和副作用 | 不能代替智能提示范围判定 |

用户调用路径、生成的 TypeScript 提示、C# / CLR 命名空间和 AI reference 导航是不同契约层。不得因其中一层的命名调整而做跨层全局替换。

## 4. 每轮核对流程

### Step 0：记录基线和范围

1. 检查 `kb-docs` 与 Kooboo 源码工作区状态，避开无关改动。
2. 记录 Kooboo commit、核对日期、测试站点和站点配置。
3. 明确本轮产品暂停项、兼容项和计划覆盖的模块。
4. 公开站点只发布英文，但本轮仍必须同时维护中文与英文源文件。

### Step 1：生成当前智能提示清单

至少保留以下字段：

| 字段 | 说明 |
|------|------|
| `path` | 规范 JS 路径，如 `k.site.pages.get` |
| `kind` | property / method / overload / dynamic object |
| `signature` | 参数、返回类型和重载 |
| `case` | 实际提示大小写 |
| `source` | static / OpenAPI / Content / UserOptions / Commerce / Integration / Market |
| `site_condition` | 出现该提示需要的站点配置 |
| `attributes` | `KIgnore`、`KeepCase`、`Obsolete` 等 |

至少采集一个基础站点；涉及动态模块时，再采集配置了对应能力的站点。不同站点的结果不能直接合并成“所有用户都能使用”的静态清单。

### Step 2：建立文档清单

扫描以下内容：

- `docs/api/**` 中文源文档；
- `docs/en/api/**` 英文发布文档；
- `docs/.vitepress/config.mts` 侧边栏；
- `docs/api/index.md` 与 `docs/en/api/index.md`；
- 页面中的 API 路径、方法名、示例和兼容说明。

文档清单至少记录页面、标题、API 路径、示例数量、导航状态和中英对应文件。

### Step 3：执行双向差异

#### 智能提示 → 文档

识别：

- 完全缺页；
- 只有 index，没有子模块；
- 方法、重载、返回结构或动态条件缺失；
- 有文档但没有经过验证的示例；
- 中文或英文单边缺失；
- 页面存在但未加入导航。

#### 文档 → 智能提示

识别：

- 无智能提示但仍被正文或索引推荐；
- 大小写与最终提示不一致；
- 已废弃或仅兼容入口仍出现在示例中；
- 把动态站点能力写成全局固定能力；
- 文档声称 API 不存在，但当前提示面已经提供；
- 中英文内容、结构、示例或链接漂移。

### Step 4：逐项分类

每个差异必须归入以下一种状态：

| 状态 | 处理方式 |
|------|----------|
| `document-now` | 当前推荐、可验证；进入实施批次 |
| `group-existing` | 不单独建页，合入现有父模块并补导航 |
| `dynamic-framework` | 文档化获取/配置/发现机制，不硬编码站点特有实例 |
| `product-hold` | 智能提示存在，但产品暂不推荐；不写公开文档 |
| `compatibility-cleanup` | 运行时可能兼容，但无提示或已有替代；从推荐文档清理 |
| `needs-runtime-evidence` | 签名可见但行为或安全边界未证实；阻塞合入 |

分类结果进入当期实施计划。公开正文不罗列暂停项和兼容墓碑；这些决策只保存在 SOP、计划和 backlog 中。

### Step 5：分区和排批

按验证风险排序，而不是按字母或文件数量排序：

```text
只读/上下文
  → 可回滚 CRUD
  → 需要站点配置的 provider
  → 权限、发布、历史、外部服务和破坏性操作
```

一次只实施一个可独立验证、可独立 review 的模块或子模块。大模块必须先拆区，再创建文档任务。

### Step 6：按现有 API 文档 SOP 编写

实施阶段遵循 `.trellis/spec/api-documentation-workflow.md`：

- 从当前提示面锁定应写的方法集合；
- 从源码核对签名、返回值、边界和动态条件；
- 从旧文档提取线索，但不直接继承未经验证的示例；
- 中文 `docs/api/**` 与英文 `docs/en/api/**` 1:1 同步编写；
- 页面只描述当前推荐 API，不把内部源码路径和测试部署语法写入正文。

## 5. 示例验证门槛

### 5.1 证据等级

| 等级 | 证据 | 是否可作为公开示例 |
|------|------|--------------------|
| S | 仅源码、签名或 schema 核对 | 否 |
| R | 真实站点执行只读示例，并核对实际响应 | 是 |
| M | 执行变更，并用独立读取验证前后状态 | 是 |
| E | 外部 provider / 权限场景，含配置前提、成功或可控失败证据 | 是 |

所有公开代码示例至少达到 R。写操作必须达到 M；外部 provider、鉴权、发布、支付等场景按 E 验证。

### 5.2 强制规则

- ai-check 文件负责可重复执行，`curl` 或真实站点调用负责取得实际结果。
- 不能只返回 `success` 或相信被测方法自己的返回值。
- 变更类方法必须用独立查询验证状态；必要时同时验证旧对象消失、新对象存在。
- 示例中的每个方法名、参数、大小写、返回字段都必须来自本轮实际执行。
- 无法运行的示例不得合入公开文档；可先保留方法说明并把任务标为 `needs-runtime-evidence`，但不要补猜测代码。
- 每次最终写入后重新执行验证；写入前的成功证据会被后续改动失效。

### 5.3 内部证据

验证记录放在不发布的本地目录：

```text
.local-review/kscript-api/<module>/
├── README.md
├── completion-snapshot.json
├── ai-check-source.ts
├── curl-result.json
├── before.json
├── after.json
└── notes.md
```

历史证据只可作为检查清单，不能直接作为当前版本通过的证明。

## 6. 中英双语同步

虽然当前正式站点只发布 `docs/en/api/**`，每次改动仍必须：

1. 同时修改 `docs/api/**` 与 `docs/en/api/**`；
2. 保持文件路径、标题层级、表格行、API 列表、代码示例和链接 1:1；
3. 代码、API 路径、参数名、返回字段和 URL 不做翻译；
4. 英文构建与导航只引用英文树，中文树继续作为未发布源保留；
5. 任何单边改动都不能标记模块完成。

## 7. 每轮交付物与完成定义

### 对齐审计完成

- [ ] 保存当前 Kooboo commit、站点条件和最终提示快照
- [ ] 完成提示 → 文档、文档 → 提示双向差异
- [ ] 每项差异已分类，并记录产品暂停项
- [ ] 形成按风险排序的分区实施计划

### 单模块文档完成

- [ ] 只覆盖当前提示中应推荐的 API
- [ ] 所有公开示例有 R / M / E 级当前证据
- [ ] 写操作有独立回读验证
- [ ] 中文与英文 1:1 同步
- [ ] 索引、侧边栏和站内链接无死链
- [ ] 通过聚焦 Markdown、链接和文档构建检查
- [ ] backlog 和实施计划状态已更新

Kooboo 项目不为文档核对运行全量 Vue `vue-tsc` 或 lint；只执行与改动范围相关的检查。

## 8. 需要立即停止并确认的情况

- 最终提示与源码生成规则无法对应；
- 同一路径在不同站点出现不兼容签名；
- API 有提示但产品推荐状态不明确；
- 示例需要真实凭据、付费外部服务或不可逆数据操作；
- 中文与英文无法保持同构；
- 连续验证失败且原因可能是平台缺陷，而不是文档错误。
